# 项目梳理

本文档用于从研究目标、代码结构和长期维护角度梳理当前项目，帮助后续开发时快速判断代码应放在哪里、哪些模块属于主干、哪些模块属于研究性代码。

## 1. 项目目标

当前项目围绕住宅建筑剪力墙结构智能设计展开，核心问题是：

- 给定建筑平面布局信息
- 预测哪些墙段位置应布置剪力墙
- 将预测结果继续转换为结构分析可用的标准化输入
- 接入 ETABS、OpenSees、YJK 等后端开展建模和力学分析

当前研究重点仍然是**剪力墙位置预测**，暂不涉及构件截面尺寸智能设计。预测方法本质上是数据驱动的房间级条件图神经网络，可称为 `RC-GNN (Room-level Conditional GNN)`。

## 2. 当前主线

整个项目已经可以按一条较清晰的主线理解：

1. 数据准备与标注
2. 房间级图构建
3. 剪力墙布局预测
4. 案例级推理与 FEM 拓扑生成
5. 结构后端建模与分析

与早期状态相比，现在项目不再适合按“一个个脚本”理解，而更适合按“核心能力模块 + 正式流程 + 结构后端”理解。

## 3. 顶层结构理解

当前仓库可按以下几类目录理解。

### 3.1 核心能力模块：`src/`

`src/` 放长期维护的核心实现。

- `src/data_engine/`
  负责数据预处理、DXF 提取、CAD 推理桥接、PNG 相关工具等。
- `src/axis_engine/`
  负责 CAD / 几何处理能力，例如中轴线提取、线网校准、矩形分解等。
- `src/shearwall_pred/`
  负责剪力墙预测模型的训练、评估、集成与推理相关实现。
- `src/shearwall_modeling/`
  负责 OpenSees 建模、分析与规范校核。
- `src/misc/`
  放通用工具能力。

这部分代码应视为长期维护主干，新增可复用算法应优先放在这里，而不是直接写成流程脚本。

### 3.2 正式流程与结构后端：`pipelines/`

`pipelines/` 放项目中的正式流程和结构建模后端。

- `pipelines/case_study/`
  当前最重要的正式流程目录，负责：
  - DXF 输入
  - 推理图构建
  - 模型预测
  - 对称后处理
  - FEM 拓扑生成
  - 可视化
  - 导出共享结构输入 `*_structural_input.json`
- `pipelines/structural/etabs/`
  负责 ETABS 后端建模。当前已经明确只负责结构后端，不再承担案例流程职责。
- `pipelines/yjk_pipeline/`
  当前保留为独立的盈建科流程。

现在应当明确一个原则：

- `pipelines/case_study/` 负责**生成结构结果与共享结构输入**
- `pipelines/structural/*` 负责**消费共享结构输入并调用具体结构软件后端**

### 3.3 项目级入口：`scripts/`

`scripts/` 用于放项目级入口脚本，例如：

- `scripts/shearwall_analyzer_main.py`
- `scripts/visualize_dataset_main.py`
- `scripts/misc_test_main.py`

原则上，项目级入口应尽量收敛在这里，根目录不再继续增长新的业务脚本。

### 3.4 研究与论文代码：`experiments/`

`experiments/` 现在主要用于放研究性、分析性、论文相关代码，例如：

- 消融实验
- 指标统计
- 绘图
- 对比分析
- 既有方法复现

它不再承载正式案例流程。换句话说，现在看到 `experiments/` 时，默认应该把它理解为“研究代码区”，而不是正式产品流程的一部分。

### 3.5 数据、输出与文档

- `data/`：输入数据、DXF 数据、缓存等
- `outputs/`：模型、图表、案例输出、结构输入导出结果等
- `docs/`：项目文档、结构说明、研究笔记

这类目录不承载核心业务逻辑，主要承担输入、结果与说明文档职能。

## 4. 研究主线中的各部分职责

### 4.1 数据集准备与标注

最初的问题是建筑结构图纸难以直接获得，因此前期使用开源图像数据集作为起点。原始数据是彩色构件图像，包含墙体、门、窗等信息，而模型训练更需要房间级的矢量化表示。

这部分相关能力主要在：

- `src/data_engine/`
- `src/axis_engine/`

主要工作包括：

- 图像清洗与去重
- 从图像或 CAD / DXF 中提取构件几何
- 将双线墙体转换为中心线表示
- 将布局分解为矩形房间
- 将几何结果桥接为训练 / 推理可用的图表示

### 4.2 房间级图建模

项目的一个关键设计选择是：**以房间而不是以墙段作为图节点**。

原因是：

- 住宅平面天然具有房间分区语义
- 仅按墙段切图会丢失空间组织信息
- 房间级表示更符合工程直觉

因此训练与推理阶段都尽量围绕“房间节点 + 相邻关系 + 几何特征”的图结构展开。

### 4.3 剪力墙预测

`src/shearwall_pred/` 是当前最稳定、最核心的模型模块之一，包含：

- 训练配置
- 数据增强
- 数据集与缓存
- 模型结构
- 损失函数
- 训练器
- 测试与可视化
- 交叉验证与集成推理

这一层的职责应保持清晰：它只关心**图输入到剪力墙预测结果**，不直接承担结构软件后端逻辑。

### 4.4 案例级推理与 FEM 拓扑

`pipelines/case_study/` 是现在连接“预测模型”和“结构分析”的关键中间层。

它负责：

- 从 DXF 构建推理所需的图输入
- 运行集成模型预测
- 可选地执行对称后处理
- 将房间级预测结果解析为 FEM 拓扑
- 生成共享结构输入

这里的输出不再只是用于可视化的临时结果，而是下游结构后端的标准接口。因此这一层现在已经从“案例脚本”演化为真正的正式流程。

### 4.5 结构建模与分析

当前结构分析部分分成两类：

- `pipelines/structural/etabs/`
  负责 ETABS 后端建模
- `src/shearwall_modeling/`
  负责 OpenSees 建模与规范校核

此外还有：

- `pipelines/yjk_pipeline/`
  负责独立的盈建科流程

这部分的长期方向非常明确：不同结构后端应尽量共享同一种结构输入语义，而不是各自直接依赖案例流程内部的临时字典结构。

## 5. 现在最重要的结构边界

当前项目最应该坚持的边界不是“目录名字”，而是以下职责划分：

### 5.1 `src/` 负责可复用能力

例如：

- 几何处理
- 图构建
- 模型训练与推理能力
- OpenSees 建模与分析能力

### 5.2 `pipelines/` 负责正式流程

例如：

- `case_study`: 从 DXF 到共享结构输入
- `structural/etabs`: 从共享结构输入到 ETABS 模型

### 5.3 `experiments/` 负责研究代码

例如：

- 消融
- 绘图
- 指标比较
- 既有方法复现

判断新增代码该放哪时，可以直接问一句：

- 这是可复用能力？
- 这是正式流程？
- 还是一次性研究脚本？

答案分别对应 `src/`、`pipelines/`、`experiments/`。

## 6. 当前维护重点

从长期维护角度看，当前最需要保证的不是“功能越来越多”，而是“边界不要再次变乱”。具体来说：

### 6.1 不再把正式流程写回 `experiments/`

`experiments/` 已经回到研究用途，不应再次承载正式案例流程或结构后端逻辑。

### 6.2 不再把核心实现写进入口脚本

入口脚本应尽量只做参数解析和流程调用，核心实现应留在 `src/` 或 `pipelines/` 的模块中。

### 6.3 结构后端优先消费共享输入

结构后端应尽量面向：

- `FEMInput`
- `*_structural_input.json`

而不是直接依赖案例流程内部细节。

### 6.4 研究脚本允许临时性，但不应反向污染主干

研究和论文工作难免需要快速试验，但不应把临时代码反向沉淀到正式流程目录中。

## 7. 后续研究方向

目前主线仍然是剪力墙位置预测，但从工程实践角度，后续研究可以继续沿以下方向展开：

- 基于预测得到的初始结构布置，进一步做构件尺寸优化
- 用更统一的结构输入接口接入不同分析后端
- 提升结构评估速度，支持更高频率的方案搜索与筛选
- 利用已有开源数据继续构造大量可分析的结构样本

从实现角度看，这意味着 `case_study -> shared structural input -> structural backend` 这条链会越来越重要。

## 8. 结论

当前项目已经不再是一个单纯的“PNG 转 DXF”工具仓库，而是一个围绕剪力墙布局预测与结构分析逐步扩展形成的研究代码平台。

如果只用一句话概括当前结构：

- `src/` 是能力层
- `pipelines/` 是正式流程层
- `experiments/` 是研究层
- `data/` / `outputs/` / `docs/` 是输入输出与文档层

后续维护时，只要始终守住这个分层，项目即使继续增长，也不会重新回到无序堆积的状态。
